# 4. Boot Fragments by Extension

## 1. Scope

The BOOT_MEMORY of a platform is assembled from one assembly fragment per extension, kept next to the RTL of the extension. Each fragment leaves in a known state the part of the core that its extension introduces, and the program that runs afterwards (the picolibc `crt0`, a real-time operating system or a test) starts from that state. The BOOT does not set up `sp`, `gp`, `tp`, `.data` or `.bss`, which belong to the `crt0`.

The Core requires no extension. A platform that turns on only the RV32I or RV32E base includes no instruction of these fragments.

## 2. Inclusion contract

The `boot_core.S` of Insper-RISC-V always includes the five files, after the `boot_config.h` generated by Tools, with no `#if` on the side of the includer. Each fragment turns itself off with its own macro.

| File | Macro that turns the fragment on | Without the macro |
| :--- | :--- | :--- |
| `src/Zicsr/boot.inc` | `RV32_HAS_ZICSR` | No instruction |
| `src/Zicntr/boot.inc` | `RV32_HAS_ZICNTR` | No instruction |
| `src/Zihpm/boot.inc` | `RV32_HAS_ZIHPM` | No instruction |
| `src/Sscofpmf/boot.inc` | `RV32_HAS_SSCOFPMF` | No instruction |
| `src/Zifencei/boot.inc` | `RV32_HAS_ZIFENCEI` | No instruction |

The inclusion order is fixed and is the one of the table. The Zicsr fragment comes first because it turns the interrupts off before any other CSR changes, and the Zifencei one comes last because `fence.i` is the last initialization instruction.

Each fragment obeys five rules.

| Rule | Value |
| :--- | :--- |
| Registers | Only `t0`, `t1` and `t2` (`x5` to `x7`, which exist in RV32E), and in practice only `t0` |
| Labels | No global label. The loop fragments use local assembler symbols that do not reach the symbol table |
| Data and stack | No data, no memory access, no stack |
| External symbol | `rv32_boot_trap`, referenced by the Zicsr fragment and defined by the includer, at an address that is a multiple of 4 |
| Base | No dependency on `RV32_IS_E`, and no register above `x15` |

The `rv32_boot_trap` symbol is a safe handler, which never returns to the interrupted code.

## 3. State each fragment leaves

| Extension | State after the fragment | Manual section |
| :--- | :--- | :--- |
| Zicsr | `mstatus` cleared (`MIE` and `MPIE` at 0), `mie` cleared, `mscratch` cleared, `mtvec` with `BASE` at `rv32_boot_trap` and direct `MODE`. With `RV32_HAS_INTERRUPTS`, `mip` is also cleared | Volume II, 2.1.1.6, 2.1.1.7, 2.1.1.9 and 2.1.1.13 |
| Zicntr | `mcycle`, `mcycleh`, `minstret` and `minstreth` at 0, and bits 0 and 2 of `mcountinhibit` at 0 (both counters run from the end of the fragment) | Volume I, chapter 6, section 6.1, and volume II, 2.1.1.10 and 2.1.1.12 |
| Zihpm | `mhpmevent3` to `mhpmevent31` at 0, `mhpmcounter3` to `mhpmcounter31` and the high halves at 0, and bits 3 to 31 of `mcountinhibit` at 0 | Volume I, chapter 6, section 6.2, and volume II, 2.1.1.10 and 2.1.1.12 |
| Sscofpmf | `mhpmevent3h` to `mhpmevent31h` at 0 (`OF` and `MINH` cleared) and bit 13 of `mip` (`LCOFIP`) at 0 | Volume II, chapter 14 and sections 3.1.9 and 3.1.10 |
| Zifencei | No CSR. Executes `fence.i` | Volume I, chapter 4 |

The BOOT can run again without a hardware reset, when the test wait point restarts from `_reset`. For this reason the fragments assume no CSR reset value and write every value that the known state requires.

### 3.1. Value choices

| Value | Choice |
| :--- | :--- |
| `mstatus = 0` | Turns the global interrupts (`MIE`) off and clears `MPIE`, so a stray `mret` does not reopen the interrupts. `MPP` is fixed to machine in the Core |
| `mtvec.MODE = 0` | The direct mode takes every trap to `BASE`, which is enough for a handler that only handles failure. The vectored mode exists only with `RV32_HAS_INTERRUPTS` |
| `mip` | The software, timer and external bits mirror the platform and the program does not write them. The fragment writes zero to `mip` only for the bits the hart lets it write |
| `mcounteren` | Not written. The Core has only M mode, and the manual says the register must not exist in that case |
| `mcountinhibit` | Zicntr inhibits `mcycle` and `minstret` only while the halves are written and releases both at the end, and Zihpm releases the event counters at the end. The two fragments touch disjoint bits, so the presence of one does not depend on the other |
| `mhpmevent = 0` | Event 0 is "no event", so the counter does not count until the application picks an event |
| Zero before release | The event selectors are cleared before the counters, and the inhibition is released only after both, so no counter counts during the cleanup |
| `mip.LCOFIP` | A counter may have overflowed between the Zicsr fragment and the Zihpm one of an earlier run, so the Sscofpmf fragment clears the pending bit after clearing `OF` |

### 3.2. Partially implemented counters

The Core implements only the first `hpm_counters` event counters, but it answers all 29 addresses. An index without a counter reads zero and ignores the write, with no exception. The Zihpm fragment writes the 29 indices without consulting `hpm_counters` or `hpm_width`, and the result holds for any value of those generics.

## 4. Extensions without a fragment

The extensions below have no state to initialize, so the Core has no fragment for them.

| Extension | Reason |
| :--- | :--- |
| M and Zmmul | The multiply and divide unit keeps no state between instructions |
| Zicclsm | Only defines the misaligned access behavior, with no register |
| Zicond and Zimop | Instructions with no architectural state of their own |
| Zihintntl and Zihintpause | Hints that the core executes as `NOP` |
| Interrupts and access faults | The state lives in the Zicsr CSRs. With `RV32_HAS_INTERRUPTS` the Zicsr fragment clears `mip`, and with `RV32_HAS_ACCESS_FAULTS` the `mtvec` already covers what there is to initialize |

## 5. Size

The size of each fragment with its macro on, in 4-byte instructions, does not depend on the base.

| Fragment | Instructions | Bytes |
| :--- | ---: | ---: |
| Zicsr, without `RV32_HAS_INTERRUPTS` | 6 | 24 |
| Zicsr, with `RV32_HAS_INTERRUPTS` | 7 | 28 |
| Zicntr | 6 | 24 |
| Zihpm | 89 | 356 |
| Sscofpmf | 31 | 124 |
| Zifencei | 1 | 4 |

With every fragment on the total is 536 bytes, which fits the 4 KiB BOOT_MEMORY together with the bank selection and the CRC validation.

## 6. Verification

The scripts are in `tests/boot` and run with the toolchain of the `ci-elf` image (prefix `riscv32-unknown-elf-`) and Spike.

```bash
make test-boot
```

| Script | What it checks |
| :--- | :--- |
| `assemble.sh` | Each fragment off generates zero bytes, even with every other macro on. On, it generates the instruction count of section 5. In every valid combination of the macros of the five extensions, the output is the ordered concatenation of the fragments, `fence.i` is the last instruction when present, only `x0` and `x5` to `x7` appear, and there is no data or symbol besides `rv32_boot_trap`. The macros of the stateless extensions and RV32E do not change the output |
| `spike.sh` | Dirties the state each extension clears, runs the fragments on Spike with the matching `--isa` and checks the state after them, besides checking that no other register changed. It also runs each fragment alone |

The Spike program ends on the HTIF `tohost`, and the failure code identifies the check that failed.

| Code | Check |
| ---: | :--- |
| 1 | `MIE`, `MPIE` or `MPRV` of `mstatus` different from 0 |
| 2 | `mie` different from 0 |
| 3 | `mscratch` different from 0 |
| 4 | `mtvec` different from the address of `rv32_boot_trap` |
| 5 | `LCOFIP` of `mip` different from 0 |
| 6 | A bit of `mcountinhibit` that the fragment clears different from 0 |
| 7 | `mcycleh` different from 0 |
| 8 | `minstreth` different from 0 |
| 9 | `mcycle` above 4095 |
| 10 | `minstret` above 4095 |
| 11 | Some `mhpmevent`, `mhpmcounter` or high half different from 0 |
| 12 | Some `mhpmeventh` different from 0 |
| 20 | A register outside `t0` to `t2` changed |
| 30 | Trap with the dirty state |
| 31 | Trap in `rv32_boot_trap` |

Spike keeps no value in the `mhpmcounter` counters or in the selectors with no modeled event, which read zero, so for those the check confirms that the fragment accesses the 29 indices without a trap. The write of zero to each counter in the RTL is covered by the tests of the Zihpm event bank.
